vio documentation

vio is a small agent that looks after Linux servers over SSH. You talk to it in plain language; it investigates with read-only tools and fixes things through plans you approve.

How it works

vio splits the work into two loops. The model proposes: it reads logs, configs and system state with observe tools, and when a change would help it calls change tools that only produce a dry run. The code disposes: vio turns those proposals into a plan, checks it against a policy written in code, asks you, and then runs exactly what you approved, verifying and rolling back as needed. The model is never in the execution loop.

investigate→propose→policy→your approval→backup→guard→apply→verify→audit
  • Agentless. Nothing is installed on your servers. The only state vio leaves is under /var/lib/vio (backups and guards).
  • Reviewable. Every change shows a diff, its risks and how it will be undone. Your approval binds to the plan's hash.
  • Hard to lock yourself out. SSH and firewall changes arm a dead-man switch on the host that reverts them unless a fresh login succeeds.
  • Private. Secrets are masked before anything reaches the model or the audit log.

Install #

vio is one binary for Linux, macOS and Windows. The installers download the latest release, check its SHA-256 checksum, and put vio on your PATH.

macOS / Linux

curl -fsSL https://raw.githubusercontent.com/ThembinkosiThemba/vio/main/site/install.sh | sh

Windows (PowerShell)

irm https://raw.githubusercontent.com/ThembinkosiThemba/vio/main/site/install.ps1 | iex

To pin a version, set VIO_VERSION=v0.1.0 first. To build from source you need Go 1.26 or newer:

go install github.com/ThembinkosiThemba/vio/cmd/vio@latest

Your servers need nothing beyond SSH and a POSIX shell. To make changes, vio's login user must be root or have passwordless sudo; without it vio can still investigate, but it can't propose changes.

Quick start #

  1. Start vio. Run vio. The first time, type /setup to pick a model (Ollama runs locally; Anthropic, OpenAI and OpenRouter need an API key).

  2. Add a server. Type /add, or just tell vio about it: "add my server web-1 at 203.0.113.10, user deploy".

  3. Trust its host key. vio shows the server's SSH fingerprint. Compare it with ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub run in your provider's web console, then accept. vio never connects to a server whose key you haven't verified.

  4. Ask something. "Is anything wrong with web-1?" or "why is the disk full?"

  5. Fix something. "Turn off password logins and enable the firewall." vio proposes a plan and waits for your yes.

› harden web-1

  ✓ web-1  check_run  2.1s
  ✓ web-1  plan sshd_set settings={"KbdInteractiveAuthentication":"no",...  0.4s
  ✓ web-1  plan fw_allow port=22  0.3s
  ✓ web-1  plan fw_enable  0.3s

  plan p-7f3a91 · 3 actions · web-1 · risk: lockout
  1  web-1  sshd KbdInteractiveAuthentication=no PasswordAuthentication=no  change · guard 2m00s · rollback ✓
       -PasswordAuthentication yes
       +PasswordAuthentication no
  2  web-1  ufw allow 22/tcp  change · rollback ✓
  3  web-1  enable ufw  change · guard 2m00s · rollback ✓
  hash 3f2a9c41d07be815…
  Apply plan p-7f3a91? Yes / No

  ○ web-1  a1 sshd PasswordAuthentication=no
    guard armed (vio-guard-1a2b-a1, reverts in 2m0s unless a fresh login works)
    fresh SSH login ✓
  ✓ web-1  a1 sshd PasswordAuthentication=no
  ...

Prefer files to chat? vio init creates config.yaml, hosts.yaml and policy.yaml, and vio hosts add web-1 --addr 203.0.113.10 --user deploy --trust adds and verifies a server in one go.

Models #

vio talks to models through one small interface, so you can use a local model or any hosted API. Pick one with /setup (or vio setup) and switch models with /model.

ProviderKeyNotes
OllamanoneLocal models at http://localhost:11434. Start it with ollama serve; pull a model that supports tool calling.
AnthropicANTHROPIC_API_KEYClaude models via the official SDK, with prompt caching.
OpenAIOPENAI_API_KEYChat Completions API.
OpenRouterOPENROUTER_API_KEYAny model on OpenRouter.
OpenAI-compatibleoptionalvLLM, LM Studio, AI gateways: set the server URL in setup.

Keys you enter in setup are stored in credentials.yaml, readable only by you. Environment variables win over the file; VIO_API_KEY works for any provider. Keys are never logged or sent to the model.

Small local models can struggle with long tool-using sessions. If answers drift, try a larger model or a hosted one.

Servers #

Your servers live in hosts.yaml in vio's config directory. You can edit it by hand:

hosts:
  web-1:
    addr: 203.0.113.10
    port: 22
    user: deploy
    identity: ~/.ssh/id_ed25519   # optional; default is ssh-agent, then ~/.ssh/id_*
    tags: [prod, web]
    notes: |
      Caddy reverse proxy for app.example.com. Postgres is on db-1.
      Never restart during 09:00-17:00 SAST.
groups:
  prod: [web-1, db-1]
  • notes are given to the model as trusted context, so it knows what a server is for. Anything read from a server is treated as untrusted data.
  • tags feed policy: prod hosts never get auto-approved changes, and your own rules can match tags.
  • groups work anywhere a host name does, e.g. vio check prod.

Host keys

vio verifies SSH host keys strictly. It reads your ~/.ssh/known_hosts and its own known_hosts, and refuses unknown keys rather than trusting them on first use. Record a key with vio hosts trust web-1 (it shows the fingerprint and asks), or non-interactively with --fingerprint SHA256:….

Authentication

vio uses ssh-agent first, then the identity file, then your default keys. Encrypted keys prompt for a passphrase once per session; it stays in memory. vio never uses password authentication, agent forwarding or port forwarding.

Chatting with vio #

Run vio and type. Each reply ends with a footer showing the mode, the model, tokens used and time taken. While vio works you see each tool call and how long it took. Press Ctrl+C to stop a reply; on an empty line it quits.

CommandWhat it does
/setup, /modelChoose the provider; switch the model.
/hosts, /add, /rmList, add and remove servers.
/trust [name]Verify and trust a server's SSH key.
/check [name]Run the security baseline (no model involved).
/ping [name]Test connections and show basic facts.
/rollback <id>Undo an applied plan.
/clearStart a new conversation.
/usage, /log, /verifyTokens used; recent audit entries; verify the audit chain.
/resetForget settings, keys, servers, policy and history (you choose which).

For a one-off question, use vio ask "is web-1 healthy?". ask is always read-only.

Modes

The max_tier setting decides which tools the model gets:

  • observe: read-only. vio explains what it would change but can't propose it.
  • change (default): typed changes such as editing a config, managing services, packages, users, SSH keys and the firewall, always with your approval.
  • dangerous: also raw commands, deleting files, removing packages or users, and reboots. These always need explicit confirmation.

Making changes #

When you ask for a change, the model calls change tools such as sshd_set, fw_allow or fs_patch. Each call is a dry run: it reads the current state and returns an action listing the exact steps, a diff, risk flags, preconditions and the rollback. Nothing has touched the server yet.

When the model finishes its reply, vio gathers those actions into one plan and shows it to you:

  • each action with its summary, tier, diff, and whether it has a rollback and a guard;
  • policy verdicts: deny blocks the plan outright; confirm flags something that needs your explicit attention, such as a dangerous tool, an irreversible step, or arguments taken from server output;
  • the plan hash. Your approval is bound to it, so a plan that changes afterwards can't be applied.

If you approve, the apply engine runs each action in order:

  1. Re-check policy right before running.

  2. Check preconditions. If a file changed since planning, vio stops with exit code 5 before touching anything.

  3. Back up every file the action will change to /var/lib/vio/backups/<apply-id>/.

  4. Arm the guard if the action could affect access. See Lockout guard.

  5. Run the steps, including native validators such as sshd -t, nginx -t, visudo -c or caddy validate, before anything reloads.

  6. Verify with probes: the service is active, the setting took effect, a fresh SSH login works.

  7. Disarm the guard on success, or roll back on any failure, and record everything in the audit log.

vio stops at the first failed action. Earlier actions stay applied unless you pass --atomic to vio apply, which rolls everything back. Afterwards the model explains the outcome, and vio prints the apply id you can use to undo it.

vio only runs the steps recorded in the approved plan. Apply never re-derives commands from the model's arguments, so what you saw is what runs.

Security baseline #

vio check runs a deterministic security baseline with no model, so it works offline and in CI. It checks hosts in parallel (8 at a time).

$ vio check web-1
● web-1  Ubuntu 24.04.1 LTS · systemd · apt · ufw (inactive)
  ✗ high     VIO-SSH-002  SSH password authentication disabled  PasswordAuthentication yes
  ✗ high     VIO-FW-001   Firewall active  ufw installed but inactive
  ✗ medium   VIO-PKG-001  No pending security updates  23 security updates pending
  ✓          VIO-USR-001  Only root has uid 0  only root
  ...

Checks cover SSH settings (root login, password and keyboard-interactive auth, empty passwords, X11, auth tries), the firewall and its default policy, publicly exposed services, pending security updates, automatic updates, pending reboots, brute-force protection, uid 0 accounts, empty passwords, passwordless sudo, world-writable system files, SUID binaries, clock sync, disk headroom, swap, and Docker socket or port exposure.

Fixing findings

vio check web-1 --fix               # propose a plan for the fixable findings, review, apply
vio check web-1 --fix -o fix.json   # write the plan to a file instead

Fixes are ordered safely: all SSH settings become one guarded change, and the SSH port you're connected on is allowed before the firewall is turned on.

In CI

vio check prod --json --fail-on high

--json prints one JSON object per host. vio exits with 1 if any failing finding is at or above --fail-on (info, low, medium, high, critical or none; default high).

Plans as files #

Plans are JSON files, so you can review them, commit them, or have someone else approve them.

vio plan -H web-1 "install fail2ban for sshd" -o plan.json   # the agent proposes; nothing runs
vio apply plan.json                                          # review, approve, apply

vio apply recomputes the hash and refuses a plan that was edited after it was made (exit code 3). Useful flags:

  • --yes: approve without asking, but only when every action is change tier and policy has nothing to confirm. Dangerous actions, irreversible steps, tainted arguments and prod-tagged hosts still need you.
  • --atomic: if an action fails, roll back the ones already applied.
  • --approve-only: review and record your approval in the file without applying it. A second person, or a CI job, can then run vio apply plan.json and it applies without asking, as long as the file is unchanged.

Approvals in plan files are bound to the plan's hash but aren't signed yet. Anyone who can write the file and run vio could approve it. Keep plan files where only operators can write them.

Rolling back #

Every apply prints an id such as x-1a2b3c4d. To undo it later:

vio rollback x-1a2b3c4d

vio restores the backed-up files and runs each action's rollback commands, newest first. Access-affecting rollbacks are followed by a fresh-login check. Apply records live in vio's state directory under applies/, and backups stay on the server under /var/lib/vio/backups/.

Rollbacks are as good as their inputs: package downgrades need the old version to still be in the repository, and anything that changed the same files after the apply will be overwritten. Actions marked irreversible (such as shell_exec and user_remove) can't be rolled back, which is why they always need explicit confirmation.

Watching for drift #

vio watch re-runs the baseline on a schedule and reports findings that appear or get resolved.

vio watch prod --every 1h --webhook https://hooks.example.com/vio
vio watch web-1 --once

With --webhook, each change is POSTed as JSON: {"host", "new", "resolved", "at"}, plus "error" when a host is unreachable. The payload is redacted before sending. Run it under systemd, cron or your CI scheduler.

MCP server #

vio mcp exposes vio's read-only tools over the Model Context Protocol (stdio), so another agent or editor can inspect your servers through vio's allowlist, secret masking and audit log. It can never change anything: change tools and inventory edits aren't offered, and calls to them are refused.

{
  "mcpServers": {
    "vio": { "command": "vio", "args": ["mcp"] }
  }
}

Servers must already be in your inventory with trusted host keys, and encrypted SSH keys must be loaded in ssh-agent, because the MCP server can't prompt you.

Lockout guard #

Any action that could cut off your access (SSH settings, firewall rules, users, authorized keys, sudoers, network config) carries the lockout risk and runs under a dead-man switch:

  1. Arm. vio uploads a revert script to /var/lib/vio/guards/<id>/ and schedules it on the server itself with systemd-run --on-active, or a detached timer where systemd isn't available.

  2. Apply the change, validating config before reload.

  3. Probe with a brand-new SSH connection, with fresh TCP and full authentication. An existing session can survive a broken sshd or firewall, so it proves nothing.

  4. Disarm on success. On failure vio rolls back over the existing session if it can; if it can't, the server reverts itself when the window ends and vio reconnects to confirm (exit code 6).

The window is guard_window in config.yaml: default 2 minutes, minimum 30 seconds. vio refuses to make a lockout-risk change if it can't arm the guard.

Policy #

Policy is code, not a prompt. Every action is evaluated before you're asked and again right before it runs, and the most restrictive decision wins: deny blocks, confirm needs your explicit approval (never covered by --yes), and allow lets it through.

Built-in rules

RuleDecisionWhat it does
tier-ceilingdenyTools above max_tier never run.
ssh-port-firewalldenyNever deny your SSH port, and never enable a firewall or default-deny unless your SSH port is already allowed, or allowed earlier in the same plan.
operator-accountdenyNever lock or remove the account vio logs in with, or remove its last SSH key.
sshd-keep-accessdenyNo PermitRootLogin no while logged in as root, no disabling public-key auth, and AllowUsers must include your login user.
protected-pathsdenyNo writes to /boot, /etc/fstab, GRUB, /etc/passwd, /etc/shadow, /etc/group and similar.
fs-remove-pathsdenyfs_remove only works under /tmp, /var/tmp, /var/log and /var/cache.
confirm-dangerousconfirmDangerous-tier tools and irreversible actions.
confirm-taintedconfirmArguments that came from server output rather than from you, such as an SSH key found in a file.
confirm-prod-autoapproveconfirm--yes doesn't apply to hosts tagged prod.

Your own rules

Add rules in policy.yaml in vio's config directory. They can only restrict: deny or confirm. Every field you set must match; within a field, any value can match. tools and hosts accept globs.

rules:
  - id: no-reboots-in-prod
    decision: deny
    tools: [host_reboot]
    tags: [prod]
    message: Reboot prod in a maintenance window, by hand.

  - id: review-db-packages
    decision: confirm
    tools: ["pkg_*"]
    hosts: ["db-*"]

  - id: no-destructive-commands   # fields: tools, hosts, tags, tiers, risks
    decision: deny
    tiers: [dangerous]
    risks: [data_loss]

An invalid policy.yaml stops vio from starting, rather than silently running without your rules.

Secrets #

All tool output passes through redaction before it reaches the model or the audit log. vio masks private keys, cloud and API tokens (AWS, GitHub, GitLab, Slack, Stripe, Google, OpenAI/Anthropic-style keys), JWTs, passwords in URLs, password hashes, and values of variables named like PASSWORD, SECRET, TOKEN or API_KEY. Each secret becomes [REDACTED:kind:hash], so the model can tell secrets apart without seeing them.

Some files are never read at all: /etc/shadow, /etc/gshadow, SSH host private keys, users' private keys, and /etc/ssl/private/*.

Writing secrets

To put a secret into a file without the model seeing it, the model writes a reference such as secret://DB_PASSWORD. vio fills it in at apply time from VIO_SECRET_DB_PASSWORD in your environment, and the plan and audit log only ever contain the reference.

export VIO_SECRET_DB_PASSWORD='…'
vio   # "write /etc/myapp/env with DB_PASSWORD=secret://DB_PASSWORD and reload myapp"

Audit log #

Every session, observation, proposal, policy decision, approval, apply step, verification and rollback is appended to audit.jsonl in vio's state directory. Each line includes the SHA-256 of the previous line, so editing, reordering or deleting entries breaks the chain.

vio log            # recent entries
vio log -n 100
vio log --verify   # check the hash chain

Arguments are redacted before they're written. Full tool output isn't stored, only its digest.

Runbooks #

Runbooks are short markdown guides the agent reads for familiar tasks. vio ships with harden-ubuntu, disk-full, high-load and tls-renew. The model sees only their names and descriptions and reads one when it's relevant.

Add your own in the runbooks/ folder of vio's config directory. A file with the same name as a built-in replaces it.

---
name: deploy-app
description: How we deploy and roll back the app on web servers
applies_to: web
---
1. Check the app's health endpoint with run_command curl … (read-only first).
2. …

Runbooks guide the agent's reasoning but grant no permissions: policy and approval still apply.

CodeMeaning
0Success.
1Error, or vio check found failures at or above --fail-on.
2Usage error.
3Policy denied, or the plan file was tampered with.

Troubleshooting #

"The SSH host key isn't trusted yet"

Run /trust web-1 (or vio hosts trust web-1) and compare the fingerprint before accepting. If a server was rebuilt and its key changed, vio refuses to connect; remove the old entry from vio's known_hosts only once you know why it changed.

"Changes need root or passwordless sudo"

vio uses sudo -n and never types passwords. Log in as root, or give the login user passwordless sudo, for example a file in /etc/sudoers.d/ with deploy ALL=(ALL) NOPASSWD:ALL, ideally narrowed to what you need.

"Policy denies this change"

The reason names the rule. Most denials protect your access: allow your SSH port before enabling a firewall, keep your login user in AllowUsers, and don't remove the key you log in with.

Drift (exit code 5)

Something changed the file between planning and applying. Ask vio to plan again; the new plan will diff against the current file.

Ollama errors

"Connection refused" means Ollama isn't running (ollama serve). A 404 means the model isn't pulled (ollama pull <model>).
